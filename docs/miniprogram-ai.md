# 第九项：AI 与耗时任务可靠性

本项遵守用户明确要求：**不要改界面**。`miniprogram/`、`web/`、`shared/` 没有变化，页面布局、样式、文案、控件位置和交互均保持。本项只修改服务器、配置模板、回归与文档，不处理仍待收尾的预览联动，不推进第十项，不连接旧 Web 生产服务。

## 继承的实现

AI 调用仍在 FastAPI 服务端，供应商 Key 不进入小程序。歌曲分析继续使用现有 FIFO 重型队列；练唱通过短请求启动进程内任务，再轮询 Attempt。用户录音不运行 WhisperX 词级对齐；Gemini 按已有 Song Profile 目标、明确符号和演唱动作进行受限比较，保留主轨最多 4 句、次轨最多 3 段裁切及有限重试。中文/纯唱保留原有跳过分析规则。模型和供应商没有替换。

## 本次改动与前后区别

| 原行为 | 修正后的行为 |
| --- | --- |
| 同步 ffmpeg 峰值检测直接占用 async 接口线程；失败或没有峰值时放行，`-inf` 也可能放行 | 在线程执行，30 秒 subprocess 超时保留；真实静音/近静音返回证据不足，检测失败保存 failed，不把坏音频交给模型 |
| 模型未配置记成证据不足，探测异常可能使后台任务消失 | 服务配置/处理故障记 failed，使用已有安全公共错误文案；后台意外异常也保存终态 |
| 次轨第三轮空或全 uncertain 返回给服务，再被误记为录音证据不足 | 最多三轮（含首次）后仍无结论记为模型失败；明确 recording_usable=false 才保留证据不足语义 |
| 外层三轮重试叠加 SDK 默认重试，无明确练唱 HTTP 超时 | 练唱 SDK 内层 attempts=1，由外层最多三轮负责重试瞬时错误/超时/结构化验证失败；每次 HTTP 请求显式超时 |
| 用户音频首次上传失败时客户端未关闭；参考上传/解析等异常清理分散 | finally 统一删除已知远端资源并关闭 SDK 客户端，上传等待自身失败也清理已知文件；删除是尽力执行，不假报供应商删除一定成功 |
| 低置信度、未知/错类型目标可能生成“可靠”评估，重复判断可能重复计数 | 仅已知目标、相同问题类型、达到阈值的结论参与新评估；重复目标触发有限重试；没有可靠评估时不写 analyzed |
| 完整删除录音后，迟到任务可能重新写回反馈 | 后台收尾清除已删除 Take 的迟到反馈；显式 preserve_attempt 的“仅分析”清理仍保留 Attempt 与 Memory |

`server/services/practice/analyzer.py` 负责模型请求、分批/重试与临时资源；`service.py` 负责信号/目标证据、状态、Attempt 与 Memory；`server/api/routes/takes.py` 负责后台异常与删除收尾。没有新增接口或修改客户端契约。

## 超时、版本和范围

新增服务端环境变量 `VERSEVIVA_PRACTICE_REQUEST_TIMEOUT_SECONDS`，默认 60 秒，范围 1–120 秒，配置模板已同步。按已安装 google-genai 的 HttpOptions.timeout 毫秒单位传入，HttpRetryOptions.attempts=1 表示不额外重试；本地测试拦截 SDK 构造参数验证，没有使用真实 Key 发请求。

这是**练唱单次 HTTP 请求**超时，不是歌曲 Pipeline、总分析任务或每个分批的完整时限。Files 状态等待仍为既有约 60 秒轮询预算，单次网络请求也可能占用其超时；每批可涉及用户/参考上传、状态等待、模型推理和尽力删除，完整耗时可明显大于 60 秒。分批次数随录音范围增加，不承诺固定总延迟。进程仍需单 Uvicorn worker；没有引入跨进程队列、配额、AI 限频或总任务取消设施。

ffmpeg 在工作线程执行，超时由 subprocess 终止该次检测；模型同步 SDK 也在线程执行。取消 asyncio 等待不能强杀已运行的线程；已知文件按线程正常 finally 收尾，进程强退/供应商删除失败的资源回收仍须后续运行策略，不能宣称绝对即时撤回远端数据。

新服务输出为 `practice-language-v7`，启动与结果缓存均按这一版本匹配；旧 v6 成功结果不会直接复用为新分析。数据模型的旧默认值保留给已有记录读取，历史不回写、不迁移、不认领他人数据。旧历史的既有存储记录也不因本次代码修复被重算。
